One request, four moves

How a purchase gets through.

01: THE SLIP

A signed intent mandate

Cap, categories, instruments, TTL, a one-time nonce, and the agent's own playback of what the human asked. Ed25519 over canonical JSON bytes.

02: THE RULES

Ten deterministic checks

Signature, expiry, payee, method, line items, quantity, category, cap, agent identity, replay, in order, short-circuiting on the first failure. No AI in that file.

03: THE ONE CALL

Does the cart match the intent?

Strict typed JSON, provider timeout, untrusted merchant text fenced as data. If it cannot answer, every purchase requires human confirmation.

04: THE RECEIPT

Hash-chained evidence

Checks, transaction summary, intent result and verdict enter a hash-linked log that the server verifies. Separate evidence JSON carries the signed slip.

Known limitations

What this deliberately is not.

Four days. Pretending a hackathon build is production-grade is the actual red flag.

  • Keys live in memory. No hardware-backed storage, no rotation. The demo generates a keypair at startup; a real payer key belongs in a secure element or wallet.
  • Nonces are an in-process set. Replay protection does not survive a restart, and would need a shared store to survive more than one instance.
  • Razorpay test mode is optional. Add test credentials to create real Orders and verify Checkout signatures. No live-mode key is accepted.
  • Synthetic data. 1,000 generated rows with known labels. Real agent traffic is messier, and the intent check is the part that would move first.
  • Multi-instance state. Nonces and the agent registry are in-memory in this demo. A production deployment would share them across instances.
