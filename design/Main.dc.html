Razorpay already shipped agents that spend money — agentic checkout, UPI Reserve Pay, Agent Studio. The layer that decides whether the spending was allowed is the one still missing, and the merchant absorbs what falls through it.

One request, four moves
How a purchase gets through.
01 — THE SLIP
A signed intent mandate
Cap, categories, instruments, TTL, a one-time nonce, and the agent's own playback of what the human asked. Ed25519 over canonical JSON bytes.
02 — THE RULES
Eight deterministic checks
Signature, expiry, payee, method, line items, category, cap, replay — in order, short-circuiting on the first failure. No AI in that file.
03 — THE ONE CALL
Does the cart match the intent?
Strict JSON, hard timeout, untrusted merchant text fenced as data. If it cannot answer, the answer is never "allow a large purchase".
04 — THE RECEIPT
Hash-chained evidence
Every check and its reason, the verdict, the signature, the slip — appended to a log whose links anyone can verify.
Known limitations
What this deliberately is not.
Four days. Pretending a hackathon build is production-grade is the actual red flag.
Keys live in memory. No hardware-backed storage, no rotation. A real payer key belongs in a secure element.
Nonces are an in-process set. Replay protection does not survive a restart or a second instance.
No agent registry. Parchi verifies the human approved this purchase, not which agent is presenting the slip.
No live UPI integration. The field mapping is on paper; wiring it needs a PSP sandbox.
Synthetic data. 1,000 generated rows with known labels. Real agent traffic is messier.
Quantity inflation is unsolved. Five identical allowed pairs under the cap still reads as in-scope.
